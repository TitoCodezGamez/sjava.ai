# sjava.ai

Personal site for Sara Javanmardi. Static [Astro](https://astro.build) build:
one page (hero + contact form) plus a booking dialog backed by Cal.com.

Production: <https://sjava.ai>

## Run locally

```bash
npm install
npm run dev     # http://localhost:4321
```

```bash
npm run build   # static output in dist/
npm run preview
```

Node 22 is required and pinned in `.nvmrc`. Astro's floor is 18.20.8, which is
above some CI defaults, so an unpinned environment can fail to build.

## Deploy

Deployed on Cloudflare as a Worker serving static assets, building from `main`.

- **Build command:** `npm run build`
- **Output directory:** `dist`

`site` in `astro.config.mjs` must match the live domain. Canonical and Open
Graph URLs are derived from it, and social crawlers require absolute URLs.

## Booking

Real bookings against Cal.com. Its v2 `slots` and `bookings` endpoints are
unauthenticated and CORS-open, so the dialog calls them from the static page
with no backend and no secret to leak.

Cal.com owns availability, duration and buffers. The site only renders what the
API returns, so changing her hours there changes the site with no redeploy.
Account identifiers live in `CAL` in `src/config.ts`.

Two things are configured on the Cal.com event type rather than here:

- **Requires confirmation** is on. The booking endpoint is public, so this is
  what stops an automated request writing straight to her calendar.
- The **"What is this meeting about?"** field is required. It is sent as
  `title`, and a booking without it is rejected.

If the event type's fields change, check them before assuming a payload still
validates:

```bash
curl -s "https://api.cal.com/v2/event-types?username=sara-javanmardi&eventSlug=coffee" \
  -H "cal-api-version: 2024-06-14"
```

If the API is unreachable, the dialog falls back to a pre-filled email.

## Contact and CV

Neither the form nor the CV link has a backend. Both open a pre-filled message:
Gmail's web compose on desktop, and a `mailto:` on touch devices, where the
Gmail web page tends to redirect to the inbox and lose the draft.

The address is `EMAIL` in `src/config.ts`, used everywhere.

For real server-side delivery, replace the submit handler in `Contact.astro`
with a `fetch()` to a form service or a Cloudflare Function.

## Images

`public/headshot.webp` and `public/og.png` are committed, generated by scripts
rather than at build time:

```bash
node scripts/make-headshot.mjs   # after replacing src/assets/images/headshot.jpeg
node scripts/make-og.mjs         # after changing the name, title or tagline
```

Astro's `<Image>` optimises during the build, which needs `sharp` in the build
container. When it is missing, Astro falls back to `/_image?href=…` URLs that
require a server to answer and 404 on a static deploy. Pre-building avoids
depending on the build environment.

## Themes

Light and dark are defined in `src/styles/themes.css` and switch on `data-theme`
on `<html>`. Nothing outside that file contains a colour value, so a third theme
means adding one block there.

The toggle sits top right. With nothing in `localStorage` the site follows the
visitor's OS preference, including changes mid-visit; clicking the toggle stores
an explicit choice that then wins.
